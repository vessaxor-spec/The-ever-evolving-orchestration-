# Capsule 0002: Specialist Depth Survives Change

This capsule records the state of **The Ever-Evolving Orchestration** after the first full specialist-staleness remediation.

It preserves the repository at commit [`21a4b5281eab025fa5f3b76c84e823a4d202a1ea`](https://github.com/vessaxor-spec/The-ever-evolving-orchestration-/commit/21a4b5281eab025fa5f3b76c84e823a4d202a1ea), captured on **5 August 2026 at 23:12 CEST**.

It references [TEO-CAPSULE-0001](0001-2026-08-05-reference-control-plane.md), which preserved the moment when the reference control plane first existed. Capsule 0001 remains untouched.

This is not a changelog entry. It is a fixed historical record of the architectural correction that followed a 56-card specialist audit.

## Why this moment was preserved

The audit found that the specialist corpus was not failing because its practitioners were shallow.

The opposite was true.

The cards were protocol-dense, opinionated, domain-specific, and operationally useful. Their weakness was structural: durable doctrine and volatile facts occupied the same layer.

A specialist could contain an excellent decision framework beside:

- a retired API
- an obsolete standard edition
- a renamed product
- an unsupported algorithm weight
- a fixed fee table
- a universal threshold that was never universal
- a research query frozen to the year in which the card was written

That made the whole card age at the speed of its most perishable sentence.

TEO therefore adopted a new preservation principle:

> **Preserve specialist depth. Externalize the obligation to verify volatile facts.**

The remediation did not replace the specialists with shorter generic agents. It added freshness governance, source authority, applicability rules, and regression tests while retaining the authoritative practitioner specifications.

## Enduring thesis added at this moment

> **A role card is a durable operating doctrine, not a permanent database of current facts.**

The following distinction became explicit:

### Durable doctrine

- identity
- purpose
- responsibilities
- non-responsibilities
- methodologies
- decision frameworks
- authority boundaries
- safety boundaries
- collaboration and handoff rules
- output contracts
- examples

### Volatile operational knowledge

- laws and effective dates
- regulatory thresholds
- standards and adopted editions
- software versions
- APIs and parameters
- model capabilities
- pricing and fees
- platform ranking behavior
- current benchmarks
- licensing and maintenance status
- product lifecycle and vendor naming

Durable doctrine remains inside the specialist. Volatile knowledge requires current evidence when the task depends on it.

## The five remediation phases

### 1. Freshness foundation

Pull request [#20](https://github.com/vessaxor-spec/The-ever-evolving-orchestration-/pull/20) established the common architecture.

All 56 registry-defined role cards received:

```yaml
freshness_policy: live-verification-required
tools_last_verified: 2026-08-05
```

The date records the last systematic review. It does not waive live verification.

Fixed `2025` and `2026` literals inside live-search query templates were replaced with `{current_year}`. Historical dates, named editions, and source titles were preserved where they were part of the evidence rather than the query template.

The repository gained:

- `policy/specialists/freshness.yaml`
- `docs/methodology/specialist-freshness.md`
- permanent freshness regression tests

The policy introduced:

- durable, slow-moving, fast-moving, and highly volatile classes
- primary-source preference
- discovery-only treatment for low-authority secondary material
- stronger evidence requirements for high and critical risk
- failure behavior that forbids asserting an unverified volatile fact

The same phase removed the first objectively false or retired instructions, including:

- the fabricated Midjourney `--iref` parameter
- an unsupported X reply multiplier
- false completion of Chrome third-party-cookie deprecation
- retired Privacy Sandbox activation guidance
- unofficial Amazon `A10` doctrine
- the retired pre-1.0 SLSA 4 model
- conflicting FIA definitions
- discontinued `async-std`
- archived `packed_simd`
- removed Airflow SLA callback guidance

It also corrected the category taxonomy for incident command, workflow optimization, and spatial terminal engineering.

## Source-authority doctrine

The active source hierarchy at this moment was:

1. regulator, standards body, primary law, official vendor documentation, official release notes
2. original research, maintained security advisories, authoritative technical publications
3. reputable industry analysis linked to primary evidence
4. secondary summaries for discovery only
5. SEO, affiliate, or unattributed AI-generated material never used as sole support

Precision was no longer treated as authority. An exact number without evidence was considered weaker than an explicit statement of uncertainty.

## What did not change

## Known limitations

This remediation addressed the audit's systemic defect and its highest-impact findings. It did not prove that every product name, version, percentage, benchmark, fee, or low-severity implementation detail in every card would remain current indefinitely.

The following limitations remained:

- `tools_last_verified` is a review checkpoint, not proof of current applicability
- live verification still depends on the executing implementation actually consulting authoritative sources
- current evidence records are not yet maintained as a dedicated machine-readable per-claim registry
- lower-priority tool and framework details still require periodic evidence cycles
- provider APIs, live retry execution, circuit breakers, cost telemetry, and runtime enforcement remain later control-plane work
- several specialist worker bindings still lack dedicated core-worker definitions
- the planned `user_research` worker remains unresolved

The correct maintenance model is therefore continuous evidence review, not another one-time claim that the roster is permanently current.

## Next horizon

The immediate architectural horizon is to bind the preserved `feedback-synthesizer` specialist into a dedicated `user_research` worker while keeping qualitative user evidence separate from analytics, market intelligence, broad research, and UX review.

The freshness horizon is to add dated, machine-readable evidence records for volatile claims and to schedule periodic primary-source reviews by volatility class and risk.

## Message to future stewards

Do not mistake detail for staleness.

The specialist cards became valuable because they contained real doctrine, strong opinions, operational constraints, and hard-won practice. The answer to aging was not to reduce them to generic prompts.

When a fact changes:

- preserve the method
- verify the authority
- state the applicability
- remove the dead action
- add a regression test
- create a new capsule when the architecture itself changes

Do not rewrite the past to make it look current.

Make the present capable of discovering that it is wrong.

---

**The roster did not become durable by knowing every future fact. It became durable by learning which facts must never be trusted without evidence.**
