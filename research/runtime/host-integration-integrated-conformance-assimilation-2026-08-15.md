# Integrated Host Conformance and Fresh-AI Assimilation Research

**Date:** 2026-08-15
**Status:** implementation-backed research candidate
**Authority:** non-normative
**Scope:** compose accepted Host Integration controls into one process-local path and make fresh-AI assimilation evidence-bearing rather than installation-based

## Why this slice exists

After materializing and operating the exact merged TEO repository in a sandbox, the reference control plane proved materially more cohesive than repository-only inspection suggested. Routing, risk, provider-diverse verification, artifact-bound finalization, evidence, specialist governance, live-scope enforcement, and Host Integration controls all execute as real subsystems.

The same hands-on pass exposed a different gap: the accepted Host Integration controls exist primarily as independently executable research slices. There is no single composed Host Integration runtime path that proves a host uses all relevant controls together.

A second gap follows from external adoption behavior. A fresh AI can copy or install TEO, describe the architecture correctly, and then continue using its pre-existing router once the integration task ends. That would produce apparent implementation success without operational assimilation.

This slice addresses both gaps together.

## Research claim

A fresh AI or existing host should not be considered assimilated with TEO merely because it has installed, copied, read, or configured TEO material.

A process-local integration can instead require an evidence-bearing state transition:

```text
reconstitute exact TEO truth
  -> preserve host identity and host portfolio authority
  -> declare the host/TEO boundary
  -> bind to exact TEO integration freshness
  -> install a persistent TEO control-plane hook
  -> produce real TEO shadow dispatch evidence
  -> execute only bounded authorized work through the composed path
  -> replay negative controls and original premortem failure modes
  -> prove a second later task still traverses TEO
  -> emit only an evidence-bounded conformance statement
```

The key anti-handwave requirement is that **one successful integration demo is insufficient**. Continued operational use must be observed after the setup step.

## Executable implementation

`research/runtime/host_integration_integrated_conformance.py` adds a process-local research composition over accepted Host Integration controls.

### Assimilation truth

The harness derives:

- stable release;
- runtime version;
- exact revision supplied by the integrating environment;
- exact Host Integration binding identity;
- active Team/Worker/Specialist counts from executable composition;
- active live task types;
- staged but unauthorized task types;
- the uncollapsed TEO responsibility chain.

### Fresh-AI assimilation declaration

The declaration must identify TEO as `embedded_orchestration_control_plane` and must preserve:

- host identity;
- host portfolio/task-admission authority;
- TEO Mission Control routing authority for admitted work;
- provider connection after routing;
- Team/Worker/optional Specialist/Capability/Implementation/Verification separation;
- bounded selected-specialist context;
- genuine independent verification semantics;
- shadow -> bounded activation -> evidence-gated expansion;
- explicit unresolved Host Integration surfaces.

Plugin, SDK, library, finished-product, corpus-loading, parallel-router, same-session-verifier, stale-registry, false-live-scope, and hidden-residual declarations fail closed.

### Persistent control-plane hook

The harness requires a standing integration record equivalent to:

```text
TEO is required for all tasks the host admits into the TEO-governed boundary.
```

A one-time assimilation conversation is insufficient.

### Integrated governed path

The accepted active-scope probe composes:

```text
host portfolio admission
  -> TEO admission claim/revalidation
  -> exact integration freshness assertion
  -> TEO dispatch
  -> dispatch provenance
  -> restrictive host/TEO authority intersection
  -> exact execution envelope
  -> host-native bounded file action
  -> exact artifact binding
  -> independent verification record
  -> TEO finalization
```

### Negative controls

The integrated sandbox requires evidence for:

- staged `documentation` scope refusal;
- revoked host admission refusal;
- post-verification artifact mutation refusal;
- high-risk autonomy preservation;
- critical qualified-human gate preservation;
- recursive re-entry refusal.

### Continued-use proof

The process-local conformance report requires:

- at least one real shadow dispatch;
- a persistent standing integration hook;
- **at least two post-assimilation governed executions with distinct task IDs**;
- all required negative controls;
- all ten original premortem failure paths mapped to a satisfied process-local check.

This means the harness refuses to call one successful setup/demo "integrated".

## Boundaries not proved

This research does not prove:

- production host authenticity;
- remote/distributed admission authenticity;
- restart-durable assimilation or recursion state;
- compromised-host resistance;
- production scheduler enforcement;
- tenant/account/credential binding;
- production adapter package provenance;
- dynamic plugin/hook discovery;
- automatic TEO upgrade authority;
- a normative or certifiable Host Integration profile.

The persistent hook is a process-local conformance record, not proof that an arbitrary external product cannot bypass its own integration.
