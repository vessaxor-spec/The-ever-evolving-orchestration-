# TEO v1.0.0 Release Contract

**Release label:** `v1.0.0`  
**Release state:** `reference_operational`  
**Reference package:** `teo-reference-router==1.0.0`  
**Release date:** 2026-08-09

This document defines what The Ever-Evolving Orchestration v1.0.0 certifies, what it does not certify, and the conditions that must be true for the `v1.0.0` tag to be created.

Creating this document does not itself create the tag or GitHub Release. The tag may be created only after this contract is merged into `main` and the exact release candidate satisfies the acceptance gates below.

## Release claim

TEO v1.0.0 is a credible vendor-neutral orchestration specification with a runnable reference control plane at the `reference_operational` state.

The release certifies that the tagged source contains an operational reference implementation of TEO's responsibility-first control plane, including:

- Team -> Worker -> optional Specialist -> Capability -> Implementation routing,
- non-lowerable effective-risk assessment,
- capability-aware implementation eligibility,
- explicit reasoning-effort selection where policy defines it,
- guarded preview-model authorization,
- provider-diverse routine fallback,
- independent provider-diverse verification,
- conditional escalation that remains distinct from routine fallback,
- guarded live provider execution for the bounded canary scope defined by policy,
- bounded retry and canonical redispatch,
- provider-family circuit Closed/Open/Half-Open behavior and abandoned probe recovery,
- content-free provider-attempt telemetry,
- strict external JSON Schema boundaries,
- verifier-calibration instrumentation,
- blinded human-review tooling,
- a separate provisional machine-panel evidence path,
- the regulated specialist evidence and freshness pilot,
- model-freshness governance,
- provider-access separation governance, and
- reproducible CI with linked-configuration and end-to-end validation.

The Python reference router package version is aligned to `1.0.0` so the repository milestone and runnable reference package identify the same functional-v1 boundary.

## Authority boundary

The v1.0.0 release does not relax TEO's authority controls.

- Critical effective-risk work continues to require qualified human approval wherever runtime policy requires it.
- Provisional machine-panel evidence remains provisional and must never be represented as human review or human ground truth.
- Provisional evidence cannot independently authorize verifier-quality claims, broaden live execution, remove a required human-review tier, or automatically change routing.
- Preview implementations remain subject to explicit preview acceptance where policy requires it.
- Authentication or provider-access mechanism is not a model-fitness signal and must not alter routing semantics.

## Explicit non-claims

The `v1.0.0` tag must not be interpreted as claiming any of the following:

- that TEO is a fully distributed production platform,
- that independent human calibration is complete,
- that verifier quality has been established against human ground truth,
- that live execution authority has been expanded beyond the bounded scope defined by policy,
- that every specialist card has the same evidence lifecycle as the regulated pilot cards,
- that TEO provisions or owns API keys, OAuth sessions, subscriptions, service accounts, delegated identities, connectors, or credential brokers,
- that the model implementations named in the tag will remain current, optimal, available, or recommended indefinitely,
- that every future production-hardening feature is complete,
- that the release is defect-free, or
- that post-v1 stewardship and empirical evidence work is unnecessary.

Independent human calibration remains tracked through GitHub Issue #75 and is required before claims or authority changes that the governing policy reserves for human-validated evidence.

## Model and routing interpretation

A release tag is a historical reference point, not a permanent model recommendation.

The models and routing assignments captured by `v1.0.0` are the implementations selected under the evidence and provider reality available at the release boundary. Future changes in model availability, capability, pricing, safety characteristics, provider documentation, or empirical performance may justify different assignments on later versions of TEO.

The model-freshness policy governs those later decisions. A newer model triggers evaluation, not automatic promotion. Future routing changes must not retroactively rewrite the meaning of `v1.0.0`.

## Provider-access interpretation

TEO owns the routing decision. The caller or integrating runtime owns valid access to the selected implementation.

API keys, OAuth or subscription-backed sessions, delegated identity, service accounts, connectors, credential brokers, and other provider-supported mechanisms may satisfy the access boundary without changing the TEO route. Reference API-key helpers and GitHub Actions workflows are convenience harnesses, not architectural requirements.

## Release acceptance gates

The `v1.0.0` tag may be created only when all of the following are true for the exact release candidate:

1. The release contract is present on `main`.
2. `teo-reference-router` reports version `1.0.0`.
3. Reference Implementation CI completes successfully.
4. The automated test suite passes.
5. Regulated specialist evidence validation passes.
6. All reference JSON schemas parse under the declared schema dialect.
7. Linked TEO configuration validation reports `valid` with no issues.
8. The end-to-end reference example completes with an independent provider-diverse verifier.
9. There is no known unresolved issue classified as a functional-v1 release blocker.
10. Known post-v1 work, including independent human calibration, remains explicitly disclosed rather than being treated as completed.

If any gate fails, the tag must not be created until the failure is resolved or the canonical readiness policy is deliberately amended through review.

## Tag immutability

Once created, `v1.0.0` identifies one exact repository commit and must not be moved to a different commit to make history appear cleaner or newer.

If a defect is discovered after release, correct it on a later version. Do not retag a different source tree as `v1.0.0`.

## Versioning after v1.0.0

TEO uses semantic release intent for repository milestones:

- **Patch (`v1.0.x`)**: compatible defect fixes, correctness repairs, security hardening, documentation corrections, or implementation refinements that preserve the established v1 responsibility and authority contract.
- **Minor (`v1.x.0`)**: backward-compatible capabilities, routes, specialists, evidence mechanisms, runtime features, or policy extensions that preserve the v1 architectural contract.
- **Major (`v2.0.0` and later)**: intentional breaking changes to the responsibility model, public schemas or compatibility contract, governance authority boundaries, or other foundational semantics that cannot reasonably be represented as a compatible v1 evolution.

Model freshness alone does not force a major version. A model replacement may be patch or minor scope depending on whether it preserves existing behavior and authority semantics.

## Post-v1 stewardship

The following remain legitimate post-v1 work and do not invalidate the `reference_operational` release state:

- independent blinded human calibration and residual-risk acceptance,
- distributed circuit-state coordination,
- distributed telemetry export,
- streaming runtime support,
- source-backed cost attribution,
- route-outcome learning, and
- integrated qualified-human approval workflows.

These features may strengthen later TEO releases. They are not silently implied by `v1.0.0`.
